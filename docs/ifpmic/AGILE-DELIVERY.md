# IFPMIC AX — 화면을 확인하며 진행하는 개발 계획

사용자 피드백: 여러 날 작업했지만 결과를 직접 보지 못했고, 진척을 판단하기 어려웠다. 따라서 **작게 구현 → 화면 시연 → 사용자 피드백 → 다음 기능** 순서로 진행한다. 긴 기반 작업의 완료를 첫 화면 공개의 선행 조건으로 두지 않는다.

이 문서는 기존 PLAN의 **실행 우선순위와 보고 방식**을 수정한다. 원본 설계의 업무·승인 규칙, 담당 역할, 검증 의무 및 전체 최종 목표는 유지한다. 아래의 제품 주기와 기존 V/B 검증 단계를 연결해 추적한다.

## 지금 확인할 결과

- **실제 요청 저장 화면: http://127.0.0.1:8769/** — 데모 로그인 → 요청 등록 → 목록·상세 → 새로고침/동일 데이터 재시작 유지. [주기02 결과와 재실행 안내](./delivery/iteration-02/README.md). 실제 API/DB를 사용하며 합성 계정·mock 프로파일이다. 실행은 아직 연결하지 않았다.

- 실행 중인 로컬 화면: **http://127.0.0.1:4173/ifpmic.html**
- 기본 화면: 설계 JSON에서 가져온 29단계·6구간·정상/복귀 연결, 단계 검색·담당 필터·입출력·통과 조건·요구사항 상세.
- `모의 시나리오`: 정상 완료, 사람 대기, 실패 복귀, 승인 반려·복구 등 기존74개 합성 시나리오 탐색.
- 화면 데이터는 합성 시연이다. 실제 Agent/장비/업무 실행 완료로 집계하지 않는다. Paperclip 내부 장착과 실제 실행 연동의 상태도 별도로 표시한다.
- 이 주소는 실행 중인 로컬 서버에서만 열린다. 서버를 다시 시작하려면 아래 명령을 사용한다. 원격 게시나 외부 데이터 전송은 하지 않는다.

```sh
npm run build
node node_modules/vite/bin/vite.js preview --host 127.0.0.1 --port 4173 --strictPort
```

Node.js24 이상으로 실행한다. 기존 AX 서버를 사용하는 방법은 README의 `http://127.0.0.1:3000/ifpmic.html` 안내를 따른다.

## 짧은 제품 주기

현재 진행: [주기03 실제 실행 연결](./delivery/iteration-03/README.md). 먼저 full H2의 케이스별 원본 증빙 누락 검사를 보완하고 있다. 실행기 결함을 보완해 새 cache 경로에서 합성 단위119건이 통과했으며 실제 실행/주기03 완료로 집계하지 않는다. 다음 공개 결과는 저장 요청의 실제 실행 접수·run/receipt 화면이다. 현재는 mapping의 미해결 검토 표시 중6개를 독립 검토로 해소했으며, 남은469개를 실제 소스와 대조해 해소하고 새 버전490 후보를 고정하는 단계다.

| 주기 | 사용자가 확인할 결과 | 연결되는 기존 단계 | 이번 완료 조건 |
|---|---|---|---|
| 1 · 화면 공개 | 전체 workflow 탐색, 정상/실패/사람 대기 시연, 데스크톱·모바일 캡처 | V0/V1/V2의 기존 시각화 | 현재 소스로 build 및 해당 browser 검사 통과, 열리는 주소·이미지·제한 사항 제공 |
| 2 · 실제 요청 한 건 | 요청 등록 → 저장된 작업 상세 → 현재 단계/대기 사유 조회 | B01/B02, B03의 필요한 경계 | 실제 API/DB 결과와 화면이 같은 작업을 가리킴. 새로고침 후 유지, 소유권·입력 오류·중복 요청 검증 |
| 3 · 실행 한 구간 | READY 작업 → 실제 단일 실행 → 결과/증거 표시 | B03/H2 및 필요한 후속 단계 | 현재 후보의 필수 실행·예외·복구 검증 통과, 실제 run/receipt/화면 연결. 모의 결과를 실제로 집계하지 않음 |
| 4 · 사람·품질 경로 | 사람 대기/답변 → SAM/TEM/SQE 수행·판정 → 실패 복귀 | 해당 B04–B13 세부 작업 | 각 역할 책임과 판정 근거가 화면/실제 상태와 일치. 장비 조작은 사람 수행 |
| 5 · 배포와 최종 인수 | 승인 digest·제출 결과·최종 보고서와 전체 workflow | 남은 B 단계와 원래 AT32 | 최종 배포/외부 제출 승인, 전체 요구사항·AT32 실제 증빙과 독립 인수 검토 완료 |

각 행은 한 번의 큰 스프린트가 아니라, **한 화면 또는 한 사용자 흐름씩 다시 나누는 우선순위 묶음**이다. 특히4·5주기를 한 번에 구현하지 않는다. 세부 B/AT 매핑은 해당 흐름 착수 전에 확정하며, 이 표만으로 기존 필수 단계를 생략하지 않는다.

## 매 주기 수행할 검증

| 필수 항목 | 운영 방법 |
|---|---|
| 목적 | 해당 사용자 흐름을 실제로 확인할 수 있게 만든다. 최종 업무 인수와 시연 승인을 구분한다. |
| 대상 | 이번 화면/흐름, 영향을 받는 기존 기능, 연결된 요구사항과 게이트. 착수 전에 구체 ID와 파일을 기록한다. |
| 방법 | 정상·오류·경계·관련 회귀를 포함한다. 시연만 하는 주기는 UI 계약/브라우저/원본 보존을 검사하며 실제 서비스 검증의 대체로 쓰지 않는다. |
| 담당 | Code-dev 통합, TC 검증 작성/실행, 독립 Agent가 계획과 결과 검토. SAM/TEM/SQE/사람의 업무 경계 유지. |
| 합격 기준 | 사전에 정한 동작이 실제 증빙으로 확인되고, 해당 범위의 테스트가 통과한다. 未연동 기능을 동작 완료로 표시하지 않는다. |
| 예상 결과 | 열리는 화면 또는 한 건의 완결된 사용자 흐름, 명확한 시연/실제 상태. |
| 증빙 | URL·화면 캡처·검증 결과·소스/산출물 해시·커밋. 내부 SQL/로그/인증/장비 정보는 계속 비공개 보존한다. |
| 실패 복구 | 실패 증빙 보존 → 원인 수정 → 해당 단계 및 영향 회귀 재검증. 타이밍/승인/품질 기준을 임의 완화하지 않는다. |

## 주기1의 구체 검증 계획

- 목적/대상: 기존 workflow 화면을 사용자가 지금 검토할 수 있게 공개. 원본29단계,6구간,41개 연결과 기존 모의 재생·선택/필터/상세·모바일 표시.
- 방법: `npm run build`, `npm run test:ifpmic:browser`, `npm run test:ifpmic:replay`; 실제 로컬 주소를 브라우저에서 열고 캡처. 별도 정적 원본 해시 검사.
- 담당: Code-dev가 실행/전달, TC가 기존 검증 기준과 이번 결과 확인, 독립 Agent가 수정 계획을 검토.
- 합격 기준: 명령 성공, browser 오류·예상 밖 외부 요청 없음, 필수 단계/연결 및 시나리오 검증 통과, 주소와 데스크톱/모바일 이미지 제공.
- 예상 결과/증빙: `docs/ifpmic/delivery/iteration-01/`의 검증 요약과 화면 캡처. 원본 browser 결과는 gitignored workflow-artifacts에 유지.
- 실패 복구: 실패 화면/검사 기록을 유지하고 이번 UI 전달 범위로 복귀. Paperclip 장착이나 실제 업무 실행 검증은 이번 단독 화면 시연에서 수행하지 않으며, 이에 대한 완료 주장을 하지 않는다.
- 영향/잔여 위험: 이번에는 보호된 기존 AX/UI 제품 소스를 바꾸지 않는다. 로컬 정적 화면과 합성 재생만 재검증한다. 실제 API·Temporal·장비·배포 및 전체 AT32 위험은 계속 남아 있으며 후속 주기에서 검증한다.

## 앞으로의 진행 보고

매 주기 종료 시 다음 여섯 항목만 먼저 전달한다.

1. **바뀐 결과:** 사용자가 할 수 있게 된 행동.
2. **직접 확인:** 열리는 URL과 화면 이미지.
3. **실제 검증:** 통과/실패한 검사와 범위.
4. **현재 제한:** 모의/미연동/미검증 기능.
5. **다음 한 가지:** 다음에 보여줄 사용자 흐름.
6. **기록:** 커밋과 push 결과.

전체16단계 중 검증 완료2단계라는 기존12.5%는 동일 비중의 단계 완료율이다. 제품 기능의 작업량 비중을 나타내지는 않는다. 앞으로는 이 수치와 함께 **시연 가능 / 실제 연결 / 검증 완료**를 산출물별로 보여준다. 테스트 개수나 문서 개수를 전체 제품 완성률로 환산하지 않는다.

동시에 진행하는 제품 흐름은1개로 제한한다. 기반 결함은 그 흐름을 실제로 막는1개를 우선 처리한다. 기존 H2 증빙 보완 소스는 별도 체크포인트로 보존하고, 전체 실행을 승인한 상태로 바꾸지 않는다. 매 주기 결과를 보여준 뒤 사용자 피드백을 다음 우선순위에 반영한다.
