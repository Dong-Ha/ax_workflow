## 다음 사용자 흐름 순서

| 순서 | 한 회차의 사용자 결과 | 완료 신호와 경계 |
|---|---|---|
| 1. 실패 원인 확인 | claim 만료 timeout의 작은 재현과 원인 설명 | 증거로 원인을 확정하고 좁은 수정·검증 범위를 정한다. 원인 미확정이면 추측을 사실처럼 기록하지 않는다. |
| 2. 요청 접수 표시 | 저장된 요청 하나를 격리된 로컬 PostgreSQL/Temporal에 실제 접수하고 같은 job/run/receipt를 I02 화면에서 확인 | 변경된 source·환경·계약·ACL과 격리·cleanup 절차를 고정해 작은 end-to-end 통합 검사를 수행한다. full490을 선행조건으로 두지 않는다. 실제 `QUEUED`는 실제 엔진 receipt가 일치할 때만 표시한다. 전체 H2/AT/운영 수용은 별도다. |
| 3. 모의 작업 완주 | 실제 로컬 서비스에서 제한된 모의 작업 한 건의 실행·결과 저장·조회 연결 | 실제 작업과 분리된 mock 모드임을 표시하고 상태 이력·재시작 경계를 확인한다. |
| 4. 사람 대기와 재개 | 질문/사람 제출 후 같은 작업이 이어지고 새로고침·재시작 뒤에도 상태를 복구 | 사람 역할과 원래 gate를 보존하며 응답 없는 자동 통과를 금지한다. |
| 5. 첫 실제 사례 | I2C 읽기 오류 처리와 정상·실패 KUnit 사례 확인 | 승인된 저장소·toolchain·품질 환경을 사용하고 소스, TC, 실제 실행 증거를 함께 수용한다. 장비·배포는 별도 승인이다. |

각 회차에서는 표의 행동 하나만 목표로 고정한다. 기술 기반 작업은 그 행동을 완료하는 데 필요한 범위로 제한하고, 독립적으로 보여줄 수 있는 사용자 결과가 생기면 다음 기반 작업 전에 전달한다.

## 진행 현황과 검사 도구

현재 흐름·완료 조건·상태는 저장소의 단일 기준 파일 `docs/ifpmic/delivery-plan.json`에 기록하고, 루트 `/delivery.html`에서 같은 데이터를 보여준다. 흐름이나 상태를 바꾸면 JSON을 함께 갱신한다. 대시보드에 표시된 단계 완료 수는 원본 필수 단계의 수용 상태를 대체하지 않는다.

- `npm run ifpmic:delivery`: 기본 목표 행동과 검사 범위를 출력한다. `--level integration|acceptance`는 해당 수준의 미충족 조건을 출력한다.
- `npm run ifpmic:delivery:check`: 현재 admission 흐름의 순수 Python protocol/workspace 검사와 전달 도구 Node 검사를 실행한다. DB/Temporal/서비스를 시작하지 않는다.
- `--level integration` 또는 `--level acceptance`: 해당 단계의 남은 필수 조건을 출력한다. `--level integration|acceptance --run` 실행기는 미구현이며 종료 코드 2로 실패한다. 이 CLI 제한은 V4 절차에 맞게 준비·검토된 별도 실제 DB/Temporal 통합 실행을 막지 않는다.

선택한 검사의 통과는 개발 피드백이다. 사용자 흐름·UI 상태나 전체 인수 상태를 자동 승격하지 않는다. 기존 full490 runner와 원본 H2 수용 조건은 별도로 보존한다.

## 검증과 완료 보고

개발 중에는 변경된 경계에 맞는 빠른 단위/API/browser 검사와 필요한 회귀만 선택한다. 좁은 mock 검증은 화면 흐름·상태 연결을 개발하는 데 쓸 수 있다. source·환경·계약·권한·격리·자원 정리가 준비되면 실제 DB/Temporal을 사용하는 제한된 로컬 통합 검사도 허용하며, 그 결과와 범위를 보고한다. 이는 실제 전체 H2, AT, 장비 실행 또는 운영 준비를 수용했다는 뜻이 아니다. 실제 경로의 보안·권한·개인정보·멱등성 조건은 해당 단계의 계약과 검증을 유지한다.

한 번 실패하면 원시/private 증거와 실행 후보를 고정하고, 실패 사례를 작은 재현으로 좁혀 원인을 확인한다. 원인·변경 범위·영향받는 검사·복구 방법을 기록하고 필요한 독립 검토 후 수정한다. 무관한 490건 전체를 수정 확인용으로 즉시 반복하지 않는다. 전체 회귀와 원본 수용 게이트는 통합·최종 수용 시 수행한다. 기존 V9 승인·실패 결과는 후속 후보의 승인으로 재사용하지 않는다.

회차 종료 시 다음 항목을 짧게 보고한다.

- 사용자가 새로 할 수 있는 행동과 URL/캡처
- mock/실제 구분, 목표·통과·실패한 검사와 아직 검증하지 않은 경계
- 완료된 사용자 흐름과 16단계 완료 수를 별도 표기
- 실패 원인과 다음 조치 한 가지
- 관련 커밋과 push 상태

새 사용자 기능이 없으면 **새 기능 없음**이라고 밝힌다. 테스트 건수·문서 수·커밋 수를 제품 진척률로 환산하지 않는다. 기존 증거와 역사적 세부는 [주기03 기록](./delivery/iteration-03/README.md), [재개 안내](./RESUME.md), 커밋 이력에서 확인한다.
