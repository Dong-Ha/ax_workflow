# IFPMIC AX — 사용자에게 보이는 결과부터 전달하기

긴 기반 작업이 끝날 때까지 시연을 미루지 않는다. 한 번에 사용자 흐름 하나를 진행하고, 화면·검증·제한을 함께 보고한다. 이 문서는 실행 우선순위와 보고 방식을 정한다. 원본 설계의 요구사항, 역할, 승인 경계와 검증 의무는 [PLAN](./PLAN.md) 및 해당 게이트를 그대로 따른다.

## 현재 상태 · 2026-10-23

- 필수 단계 **2/16 = 12.5%**. 동일 가중치의 완료 단계 수이며 작업량이나 최종 인수율이 아니다.
- [정적 진행 현황판](http://127.0.0.1:4173/ifpmic-progress/delivery/status.html)과 workflow 탐색 화면(http://127.0.0.1:4173/ifpmic.html)이 로컬 4173에서 열린다. 현황판의 검토된 캡처는 실제 490 실행 시작 전 상태다. 해당 체크포인트는 커밋 `18e3bf7` 시점의 기록이며 [검토 결과](./delivery/status-result-review-2026-10-23.json)도 당시 상태로만 수용한다.
- 전달된 두 흐름은 ① 29단계·6구간·41연결 탐색과 74개 합성 시나리오, ② 합성 계정/mock 프로파일을 이용한 과거 로컬 API·DB 요청 저장이다. 요청 API `8769`는 현재 중지 상태이며, 두 번째 흐름의 [과거 검증과 재실행 안내](./delivery/iteration-02/README.md)는 현재 서비스 가동을 뜻하지 않는다.

- 다음 사용자 목표는 **저장 요청 → 실제 실행 엔진 접수 → 같은 작업의 run/receipt와 QUEUED 표시**다. 정상 접수, 중복 방지, 권한 오류, 새로고침 유지를 확인한다. 사람·품질 역할, 장비, 배포와 원래 AT32 인수는 별도 완료 조건으로 남는다.

역사적 상세와 이전 체크포인트는 [RESUME-HISTORY](./RESUME-HISTORY-2026-10-21.md)와 [주기 03 기록](./delivery/iteration-03/README.md)에 보존한다. 그 문서의 과거 수치나 실행 지시는 현재 상태로 해석하지 않는다.

## 다섯 제품 우선순위

| 순서 | 사용자 결과 | 상태와 완료 기준 |
|---|---|---|
| 1 · 설계 화면 | workflow 탐색과 합성 재생 | 전달됨. 합성 결과를 실제 업무 실행으로 표시하지 않는다. |
| 2 · 요청 저장 | 요청 등록, 목록·상세와 새로고침 유지 | 과거 로컬 API·DB 저장 흐름 전달됨. API는 중지 상태이며 mock 프로파일 범위다. |
| 3 · 실행 연결 | 요청 접수, 같은 run/receipt와 QUEUED 확인 | 진행 중. 최신 V6 실제 검증은12건 중10통과·2실패,478건 미실행. 두 관측 보완·전체 수용·화면 연결이 남았다. |
| 4 · 사람·품질 경로 | 사람 대기/응답과 SAM/TEM/SQE 판단 | 각 역할의 승인과 증거가 실제 상태와 일치해야 한다. 장비 작업은 담당자가 수행한다. |
| 5 · 배포·최종 인수 | 배포 증거와 전체 요구사항/AT32 인수 | 배포 승인 및 독립 인수 전까지 미완료다. |

각 우선순위는 여러 기능을 한 번에 구현하라는 뜻이 아니다. 현재 흐름을 막는 범위만 처리하며, 필수 검증이나 승인 경계를 생략하지 않는다.

## 매 주기 기록할 여덟 항목

| 항목 | 기록 기준 |
|---|---|
| 목적 | 이번에 사용자가 확인할 행동과 완료 조건 |
| 대상 | 흐름, 영향받는 기능, 요구사항 및 게이트 ID |
| 방법 | 정상·오류·경계·회귀 검사와 시연/실제 구분 |
| 담당 | Code-dev 통합, TC 검증, 독립 검토; SAM/TEM/SQE/사람의 역할 유지 |
| 합격 기준 | 사전 정의한 동작을 증거로 확인; 미연동 기능은 완료로 표시하지 않음 |
| 예상 결과 | 열리는 화면 또는 한 건의 완결된 사용자 흐름 |
| 증빙 | URL, 캡처, 검증 결과, 해시와 커밋; 원시/private 자료는 비공개 보존 |
| 실패 복구 | 실패 증거 보존, 원인 수정, 영향 범위 회귀 확인; 기준 완화 금지 |

매 종료 보고는 바뀐 사용자 행동부터 쓴다. 검증만 진행했으면 **새 사용자 기능 없음**이라고 밝히고, 완료율·시연 가능 흐름·검증 건수를 따로 보고한다. 내부 테스트 수를 제품 완료율로 환산하지 않는다. 제품 흐름은 동시에 하나만 진행하며, 기반 작업은 그 흐름에 필요한 만큼으로 제한한다.

## 이번부터 적용하는 짧은 전달 주기

1. 회차 시작에 사용자 행동 하나와 합격 조건을 고정한다. 이번 목표는 **저장한 요청의 같은 run/receipt·QUEUED 표시**다.
2. 내부 준비·검토만 이어져 결과 전달이 밀리지 않게, 각 작업 회차 종료 시 현재 화면 또는 저장된 캡처를 먼저 전달한다. 새 기능이 없으면 그 사실과 실패 지점을 적는다.
3. 실제 검증 한 번이 실패하면 증거와 원인·다음 조치 하나를 기록한다. 새 버전 검토를 반복한 사실을 제품 진척으로 집계하지 않는다. 재시도는 수정 범위와 필요한 승인이 갖춰진 뒤 수행한다.
4. 제품 진척은 아래 세 흐름으로 보고한다. 16단계 완료율과 시험 건수는 별도 지표로 둔다.

| 사용자 흐름 | 전달 상태 | 바로 확인할 증거 |
|---|---|---|
| 설계 단계·담당·경로 탐색 | 전달됨 · 합성 재생 | [화면과 사용 순서](./delivery/iteration-01/README.md), [전체 캡처](./delivery/iteration-01/workflow-desktop.png) |
| 요청 등록·저장·다시 조회 | 로컬 검증 전달됨 · 현재 API 중지 | [검증 및 재실행 안내](./delivery/iteration-02/README.md), [캡처](./delivery/iteration-02/iteration-02-user-a-desktop.png) |
| 저장 요청의 실제 실행 접수 표시 | 미완료 · 이번 목표 | [현재 실패 기록](./delivery/iteration-03/runtime-v5-execution-status.json), [V6 보완 계획](./delivery/iteration-03/WORKER-OBSERVATION-REPAIR.md) |

V6는 활동 진행 상태 관측과 복구 준비 확인을 보완한 후보다. 같은152개 합성 검사는 통과했으나 새 관측 helper의 실제 서버 동작이나490개 전체 통과를 증명하지 않는다. V6 전체 소스·실행 전 승인은 완료됐고 실제 실행은 아래 최신 기록처럼 실패했다. 두 관측 보완 뒤 전체 실제 검증·독립 수용과 UI 연결이 남아 있다. 이번 체크포인트에서 새 사용자 기능은 없다.

## 최신 체크포인트 · V6 실제 실행 후

V6 실제 시도는 종료했다. 15묶음 목록 수집,12건 중10통과·2실패·오류/skip0,478미실행이다. 새 pending 관측과 CRASH10 복구는 통과했다. CRASH11은 실제 eligibility2개 철회 뒤 count1 기대에서, CRASH12는 원래 QUEUED 조회 성공 뒤 armed 전용 카운터 증가 기대에서 실패했다. [실행 상태](./delivery/iteration-03/runtime-v6-execution-status.json)와 [두 관측 보완 계획](./delivery/iteration-03/RECOVERY-OBSERVATION-REPAIR.md)을 따른다. [화면 연결 V2 초안](./delivery/iteration-03/ADMISSION-UI-PLAN-v2.md)은 구현 전 독립 검토 및 실제 H2 수용이 남았다. 새 사용자 화면 기능과 전체 단계 완료율 변화는 없다.

후속 두 관측 수정은 독립 계획 승인 뒤 TC에 구현했고 AST·차이만 확인했다. 수정 후 테스트/SDK/실제490은 미실행이다. 다음 행동은 새 후보 바인딩·영향받는 검토를 준비한 뒤 실제 검증으로 보완 효과를 확인하는 것이다. 기존 V6 승인은 변경된 소스에 적용되지 않는다.

V7 후보에서는 원래152 본문 검사·독립 결과 수용·전체 소스 승인까지 완료했다. 원래490/956규칙/예산은 유지했다. 다음은 정확한 실행 전 검토와 새 실제490 한 번 실행이다. [UI 연결 최신 초안은 V3](./delivery/iteration-03/ADMISSION-UI-PLAN-v3.md)이며, 실제 접수 화면은 아직 구현하지 않았다.
