# 에이전트 모니터링 대시보드 요구사항

현재 단계: requirements. 기존 workflow-artifacts 산출물은 발견되지 않았다. 이 문서는 제품 계약과 격리 작업 지침을 기준으로 개발·테스트·운영 검토의 입력을 정의한다. 이번 단계의 산출물은 이 문서와 prototype.md이며 제품 구현, 서버 변경, 배포는 포함하지 않는다.

## 제품 범위 및 용어

- 현재 공급자(provider)와 세션의 전체 스냅샷에 포함된 에이전트를 대상으로 검색 및 상태 필터를 적용한다. 원본 데이터가 제외한 에이전트를 추가로 탐색하거나 불러오지 않는다.
- 전체 수 N은 필터 적용 전 스냅샷의 고유 에이전트 수다. 일치 수 M은 검색 조건과 상태 조건을 모두 만족한 고유 에이전트 수다. 맥락 카드와 선택 상세는 M에 가산하지 않는다.
- 맥락 카드는 일치하는 후손까지의 실제 부모 경로에 있는 비일치 조상이다. 일치하는 에이전트와 맥락 조상을 제외한 비일치 형제 및 후손은 숨긴다.
- 상태 표시 문구는 전체(all), 진행 중(in progress), 완료(completed), 실패(failed), 대기(waiting)다. 기존 공통 모델의 상태를 사용하며 필터를 위해 서버 상태 해석을 변경하지 않는다.

## 기능 및 수용 기준

| ID | 요구사항 | 측정 가능한 수용 기준 |
| --- | --- | --- |
| F01 | 이름·ID·원본 역할·한국어 표시 역할 검색 | 네 필드 중 어느 하나에 검색어가 포함되면 검색 조건을 만족한다. 영문은 대소문자를 구분하지 않고 앞뒤 공백을 제거한다. 내부 공백은 유지하며 하나의 문자열로 검색한다. 빈 검색어는 모든 에이전트와 일치한다. 예를 들어 원본 역할 developer와 표시 역할 개발자는 각각 developer 및 개발자 검색에 모두 일치한다. |
| F02 | 검색과 상태를 AND로 결합 | 선택 상태가 전체이면 상태 제한이 없다. 그 외에는 해당 상태에 정확히 일치해야 한다. 이름 검색에는 일치하나 상태가 다른 에이전트는 일치 수에 포함되지 않는다. 다섯 상태 선택지가 모두 제공되고 하나만 선택할 수 있다. |
| F03 | 후손 보존과 계층 맥락 | 일치 후손은 조상이 불일치해도 표시한다. 실제 부모 경로의 모든 조상을 한 번씩 표시하고 비일치 조상에는 맥락 배지를 붙인다. 맥락 조상 때문에 숨겨진 형제를 표시하지 않는다. 필터 적용 시 일치 후손까지의 경로가 펼쳐져 있어야 한다. 새 부모 관계나 다른 프로젝트의 루트를 생성하지 않는다. |
| F04 | 전체 스냅샷 기준 집계 | 항상 일치 M / 전체 N을 표시한다. 상태별 집계를 제공할 경우에도 필터 이전 스냅샷을 기준으로 계산한다. 필터를 바꿔도 N과 상태별 전체 집계는 동일하며 스냅샷 변경 시에만 갱신된다. 맥락 카드를 포함한 화면 카드 수를 M으로 표시하지 않는다. |
| F05 | 명확한 초기화와 빈 결과 | 검색 또는 상태가 적용되면 필터 초기화 동작을 제공한다. 실행하면 검색어는 빈 값, 상태는 전체가 된다. M=0이고 N>0이면 조건에 맞는 에이전트가 없다는 안내와 초기화 동작을 표시한다. N=0이면 해당 세션에 에이전트가 없다는 별도 안내와 0 / 0 집계를 표시한다. |
| F06 | 선택 상세 유지 | 같은 공급자·세션에서 필터를 변경하거나 초기화해도 선택한 에이전트의 상세를 유지한다. 선택 에이전트가 숨겨졌다면 현재 필터에서 숨겨졌다는 표시와 필터 초기화 동작을 상세에 제공한다. 해당 에이전트를 억지로 일치 목록에 추가하거나 M을 증가시키지 않는다. 맥락 카드를 선택해도 상세를 볼 수 있다. |
| F07 | 공급자·세션 변경 | 공급자 또는 세션이 실제로 변경되면 검색어와 상태를 즉시 초기화한다. 이전 공급자·세션의 선택 상세는 제거하고 새 세션에서 에이전트 선택 안내를 표시한다. 같은 공급자·세션의 스냅샷 갱신은 필터를 유지한다. |
| F08 | 갱신 및 상세의 정확성 | 갱신된 전체 스냅샷에 동일 조건을 적용하여 M과 N을 다시 계산한다. 선택 에이전트가 스냅샷에서 사라지면 이전 상세를 계속 표시하지 않고 더 이상 이용할 수 없다는 안내를 표시한다. 새 요청에는 이전 턴 결과를 노출하지 않으며 종료 기록 없이 턴 완료를 추정하지 않는다. |
| F09 | 조작 가능성 | 검색 입력, 상태 선택, 초기화, 에이전트 선택을 키보드로 실행할 수 있고 포커스 표시와 접근 가능한 이름을 제공한다. 상태와 맥락 여부는 색상 외에도 텍스트로 구분한다. 결과 집계와 빈 결과 안내는 보조 기술로 읽을 수 있다. |

## 개인정보 및 격리 요구사항

| ID | 요구사항 | 확인 방법 및 통과 기준 |
| --- | --- | --- |
| P01 | 기존 읽기 전용 API와 서버 경계 유지 | 개발 변경 목록에 server/ 또는 어댑터, 인증, 서버 API 동작 변경이 없어야 한다. 원본 기록·설정·인증 파일을 수정하는 기능이나 호출을 추가하지 않는다. |
| P02 | 프로젝트 및 실제 부모 관계 유지 | 테스트용 합성 데이터에서 다른 프로젝트 루트와 실제 부모 관계가 없는 에이전트는 검색어가 일치해도 표시·집계되지 않아야 한다. UI 필터는 제공된 스냅샷의 범위를 확장하지 않는다. |
| P03 | 민감 데이터 비노출 | 추론, 원시 명령, 도구 입력·출력, 인증 자료를 API나 목록·상세·검색 대상에 추가하지 않는다. 표시 텍스트는 기존 safeText 처리 경로를 거친다. 합성 민감 표식을 넣은 검증에서 해당 표식이 렌더링되거나 새 응답 필드로 노출되지 않아야 한다. |
| P04 | 검색 데이터 최소화 | 검색어·선택·필터는 화면의 일시 상태로 유지하며 URL, 로그, 분석 이벤트, 영구 저장소에 기록하지 않는다. 검색 때문에 별도의 네트워크 요청을 추가하지 않는다. |
| P05 | 격리 작업 준수 | 이 작업의 파일 쓰기는 supplied workspace 안의 허용된 단계 산출물에 한정한다. 네트워크 요청, 의존성 설치, Paperclip 호출, 커밋 및 push를 수행하지 않는다. 실제 대화 기록·자격 증명·환경 값을 검증 자료나 보고서에 포함하지 않는다. |
| P06 | 보고서 최소 공개 | workflow-artifacts 보고서는 요구사항, 합성 예시, 결함, 검증 결과만 포함한다. 비공개 추론, 원시 subprocess 출력 또는 API 응답을 포함하지 않는다. |

## 후속 QA 검증 시나리오

prototype.md의 합성 스냅샷 N=6을 공통 기준으로 사용한다. 아래 검증은 후속 테스트 단계의 계획이며 이번 단계에서 실행한 테스트 결과가 아니다.

1. 이름 Build, ID dev-2, 원본 역할 developer, 한국어 역할 개발자를 각각 검색하여 지정 필드 검색이 작동하는지 확인한다. ` DEVELOPER `는 developer와 동일한 결과를 내야 한다.
2. 검색 developer + 실패: dev-2만 일치하고 review-1은 맥락이다. M=1, N=6이며 형제·다른 루트는 숨긴다.
3. 검색 테스트 + 대기: qa-1만 일치하고 lead-1과 dev-1은 맥락이다. M=1, N=6이며 일치 경로가 펼쳐져 있다.
4. 상태만 적용했을 때 진행 중=2, 완료=1, 실패=1, 대기=2, 전체=6이다. 각 필터에서도 전체 N=6을 유지한다.
5. dev-1 선택 후 developer + 실패를 적용해도 dev-1 상세가 유지되고 숨김 안내가 나타난다. 초기화하면 목록 6개와 동일한 선택 상세가 보인다.
6. 일치하지 않는 문자열을 입력하면 M=0, N=6이고 명확한 빈 결과 및 초기화 동작이 보인다. 빈 스냅샷에서는 M=0, N=0이며 별도 세션 빈 상태가 보인다.
7. 공급자 변경과 세션 변경을 각각 수행하면 검색·상태가 초기화되고 이전 선택 상세가 제거된다. 같은 세션 갱신에서는 조건을 유지하고 갱신된 전체 스냅샷 기준으로 집계한다.
8. 갱신으로 선택 에이전트가 사라진 경우 이용 불가 안내가 나타나며, 새 요청에 이전 턴 결과가 표시되지 않는다.
9. 키보드만으로 입력·상태 선택·초기화·카드 선택을 완료한다. 맥락, 상태, 결과 수를 텍스트와 접근성 정보로 확인한다.
10. 합성 프로젝트 격리·민감 표식·부모 관계·페이지 처리 자료로 P01–P06 및 기존 격리/개인정보 불변 조건을 검증한다. 페이지가 있는 경우 화면에 렌더링된 페이지 크기를 전체 수로 오인하지 않는다.

## 단계 인계 및 승인 기준

제품부는 F01–F09와 P01–P06, 프로토타입의 상태 전이를 검토한다. 개발팀은 승인된 범위의 UI 구현과 결함 수정을 담당하고, 테스트팀은 검증 및 결함 보고를 담당하며 제품 코드를 수정하거나 테스트를 약화하지 않는다. 결함은 개발팀으로 되돌린 뒤 테스트팀이 동일 시나리오로 재검증한다. 운영팀은 출시 승인 이후 로컬 배포를 담당한다. requirements 단계에서는 출시 승인이나 배포 완료를 주장하지 않는다.
