# 에이전트 모니터링 대시보드 개발 규칙

현재 단계: design. 이 규칙은 requirements.md, prototype.md, design.md 및 development-plan.md의 후속 개발·QA 경계를 정의한다. 이번 단계에서는 세 설계 문서만 작성하고 구현하지 않는다.

## 작업 경계

- supplied workspace 안에서만 작업하고 해당 단계에 허용된 파일만 작성한다. 부모 디렉터리, 실제 대화 기록, 인증 자료를 탐색하지 않는다.
- server/, 서버 API 동작, 어댑터, 인증, 원본 기록·설정은 수정하지 않는다. 프런트엔드 개선을 위한 새 서버 필드나 엔드포인트를 추가하지 않는다.
- 네트워크 요청, 의존성 설치, Paperclip 호출, 커밋, push를 하지 않는다. 일반 저장소의 커밋/push 규칙보다 이 격리 지침을 우선한다.
- 이미 설치된 React·TypeScript·Vite를 사용한다. 새 UI 프레임워크나 상태 관리 패키지를 도입하지 않는다.
- 보고서는 workflow-artifacts에 요구사항·합성 예시·결함·검증 결과만 기록한다. 비공개 추론, 환경 값, 자격 증명, 원시 subprocess 출력, API 응답을 포함하지 않는다.

## 프런트엔드 코딩 규칙

1. 기존 Agent/Dashboard 계약을 사용하고 필터 선택 타입을 별도로 둔다. waiting을 서버 AgentStatus에 억지로 추가하지 않는다. design.md의 대기 분류는 제품 확인 후 적용한다. 시간·stale·닫힌 관계로 완료·실패·대기를 추정하지 않는다.
2. 검색은 안전하게 공개된 이름(nickname), ID, 원본 role, 실제 한국어 표시 역할에 대해 수행한다. trim과 대소문자 무시 부분 일치를 공통 순수 함수로 처리한다. 필드 간 OR와 검색/상태 간 AND를 구분한다. task/result/activity를 검색 대상에 추가하지 않는다.
3. 카드·상세·검색에서 같은 역할 표시 함수를 사용한다. 알려진 역할의 한국어 문구와 원본 문자열을 함께 보존하고, 미등록 역할은 안전한 원본 fallback으로 처리한다.
4. 전체 agents는 불변 입력이다. filter를 적용한 배열로 dashboard.agents를 대체하지 않는다. 전체 고유 ID 수 N, 일치 ID 수 M, 맥락 집합과 상태별 전체 집계를 별도로 계산한다.
5. 부모 확장은 현재 전체 맵에 존재하는 실제 parentId만 따라간다. 숨긴 형제나 비일치 후손을 포함하지 않는다. 방문 집합으로 중복·순환을 차단하고 기존 형제 순서를 유지한다. 외부 노드·부모를 가져오거나 만들어내지 않는다.
6. query, status, selectedAgentId는 화면의 일시 상태다. URL, localStorage, sessionStorage, 로그, 분석 이벤트에 저장하지 않는다. 파생 집계·visibleIds를 독립적인 mutable 상태로 중복 관리하지 않는다.
7. 상세는 전체 맵에서 선택 ID로 조회한다. 필터 변경·초기화로 선택을 바꾸거나 첫 결과를 자동 선택하지 않는다. 선택 제거 시 이전 객체·task/result/activity를 유지하지 않고 이용 불가 안내를 표시한다.
8. provider/실제 sessionId 범위 변경은 필터·선택·이전 카드·집계·활동·cursor를 즉시 정리하고 요청 세대를 무효화한다. 같은 범위 폴링은 조건을 유지한다. 기존 dashboardRequest/activityRequest 방어를 확장하고 응답의 범위도 확인한다.
9. 필터로 숨겨도 유효한 선택 상세의 활동 페이지 흐름을 유지한다. 활동 페이지 크기를 에이전트 N으로 사용하지 않는다. 선택 제거/범위 변경 뒤 늦은 이전 페이지 응답이 복원되지 않도록 한다.
10. 새 스냅샷의 비어 있는 result를 이전 result로 보충하지 않는다. 종료·새 요청의 의미를 프런트엔드에서 재추론하지 않는다. React 텍스트 렌더링과 기존 safeText 공개 경로를 유지하며 HTML 삽입을 사용하지 않는다.

## 화면 구현 규칙

- 검색·상태·초기화는 label이 있는 입력과 native select/button으로 구현한다. 기본 키보드 동작을 보존하고 focus-visible 스타일을 제공한다.
- 검색·상태 변경 시 입력 포커스를 이동시키지 않는다. 전체·진행 중·완료·실패·대기의 다섯 상태 중 하나만 선택 가능하게 한다.
- 일치/전체, 활성 조건, 맥락, 선택, 상태를 텍스트로 표시한다. 색상만으로 구분하지 않는다. 중단/미확인의 원래 의미를 숨기지 않는다.
- 결과 수는 비방해 live 알림으로 제공한다. 폴링마다 전체 트리나 상세를 반복 낭독하는 live 영역을 만들지 않는다.
- 결과 없음과 빈 세션, 로딩과 오류를 구별한다. 조건이 활성화되면 명확한 초기화를 제공한다. 상세의 초기화도 같은 상태 전이를 사용한다.
- 좁은 화면에서 컨트롤과 긴 문자열이 영역을 벗어나지 않게 하고 목록 아래 상세를 유지한다. 숨겨진 선택을 보여주기 위해 목록 조건이나 집계를 변경하지 않는다.

## 책임과 검증 규칙

개발팀은 제품 변경 및 결함 수정을 소유한다. QA는 테스트 코드·하네스·독립 검증·결함 보고를 소유하고 제품 코드를 수정하지 않는다. 개발팀은 QA 테스트를 삭제·약화하거나 기대값을 임의 변경하여 통과시키지 않는다. 의미 변경이 필요하면 제품부의 결정과 요구사항 수정 후 동일 기준으로 재검증한다.

가능한 경우 좁은 탐색·반복 작업은 가장 저렴한 사용 가능한 에이전트부터 수행한다. 파일 수정 책임은 분리하고 다른 작업자의 변경을 되돌리거나 현재 단계 밖의 파일을 함께 수정하지 않는다. 주 담당자는 중요한 결론과 최종 변경 범위를 검토한다.

검증 데이터는 workspace 안의 합성 자료만 사용한다. 기존 어댑터 테스트는 프로젝트 격리·개인정보 제외·실제 부모 관계·페이지 처리를 유지하는 회귀 기준이다. 실행 권한과 하네스 범위가 불명확하면 실제 기록 조회나 네트워크 실행으로 대체하지 않고 미실행 이유를 보고한다.

빌드/테스트가 필요한 후속 단계에서는 해당 변경에 맞는 검사만 수행한다. 실패는 요구사항 ID와 재현 가능한 합성 사례로 개발팀에 반환한다. 수정 후 QA는 재현 사례와 영향 범위를 재검증하며 새 변경·실패·미해결 우려가 없으면 불필요한 반복 검증을 하지 않는다.

완료 보고는 실제 작성 파일과 검토·검증 결과를 구분한다. 설계 문서 작성만으로 기능 동작, 테스트 통과, 출시 승인, 배포를 주장하지 않는다. 중요한 결함과 대기 의미가 해결되고 출시 승인이 기록된 뒤에만 운영 단계로 인계한다.
