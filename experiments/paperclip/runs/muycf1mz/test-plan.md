# 에이전트 모니터링 대시보드 테스트 계획

현재 단계: test-plan. requirements.md, prototype.md, design.md, development-plan.md, development-rules.md와 현재 제품 계약을 검토했다. 기존 test-plan.md는 없었다. 이 단계는 계획 및 케이스 검토이며 테스트 실행, 구현 완료, 출시 승인 또는 배포를 주장하지 않는다.

## 범위와 계약 충돌

수용 기준은 F01–F09와 P01–P06 전부다. 이름·ID·원본/한국어 역할 검색, 검색과 상태의 AND, 실제 조상 맥락, 전체 스냅샷 집계, 독립 선택 상세, 범위 전환·삭제·갱신, 접근성 및 개인정보를 생략하지 않는다.

| 검토 항목 | 판단 및 처리 |
| --- | --- |
| C01 대기 의미 | requirements/prototype는 대기 상태를 요구하나 design은 기존 모델에 waiting이 없고 unknown으로 분류하는 미승인 제안을 기록했다. 제품 승인 증거는 검토한 산출물에 없다. 대기 판정의 최종 기대값 및 출시 게이트는 BLOCKED다. unknown을 실행 대기로 단정하거나 대기 테스트를 삭제하지 않는다. 제품부가 서버 변경 없는 의미를 확정하고 문서를 정합화한 후 해당 테스트를 실행한다. |
| C02 기본 선택 | 현재 제품 계약은 새 스냅샷에서만 기본 선택을 허용하지만 requirements/design은 전환 후 선택 안내와 자동 대체 제거를 요구한다. 더 구체적인 산출물 기준으로 새 범위는 선택 없음으로 검증한다. 기본 선택을 도입하려면 제품 문서에서 결정하며 이전 객체 재사용은 어떤 경우에도 금지한다. |
| C03 역할 표시 | 한국어 표시가 기존 체계에 없다는 설계 설명은 구현해야 할 차이다. 원본 및 design의 실제 한국어 문구를 모두 검색하는 기준을 유지한다. 미등록 역할은 안전한 원본 fallback으로 검증한다. |
| C04 하네스 | development-plan의 브라우저 실행 파일 미확인 기록은 실행 준비 위험이다. 스크립트 이름만으로 통과 판정하지 않는다. 후속 QA가 설치된 도구로 오프라인 합성 하네스를 준비하지 못하면 브라우저 검증을 미실행으로 보고한다. |

## 검증 층과 준비

1. 단위 검증: 검색 정규화·필드 OR·조건 AND·역할 표시·전체 집계·부모 경로·불변성 및 선택 수명 주기 상태 전이를 검증한다. 순수 함수에만 제한하지 않고 범위 전환/삭제의 상태 관리 경계도 포함한다.
2. 브라우저 검증: 합성 스냅샷을 메모리에서 공급하는 오프라인 하네스로 실제 입력, 상태 선택, 카드, 상세, 지연 응답 및 접근성 동작을 검증한다. fetch 계층은 인메모리 대체하며 실제 서버·외부 요청을 보내지 않는다. 가짜 시계와 수동 응답 완료로 폴링·경합 순서를 통제한다.
3. 회귀 및 정적 검토: 후속 QA에서 실행 가능한 합성 기존 어댑터 검증(npm test), 타입/번들 검사(npm run build), 변경 경계와 안전 텍스트 경로를 검토한다. 실제 기록 접근을 요구하는 실행은 대체 합성 경로가 없으면 미실행으로 기록한다. 서버 제품 코드를 수정하지 않는다.

합성 자료는 test-cases.md의 S1(N=6), S2, 빈 스냅샷, 갱신/삭제/경합 및 잘못된 관계 변형을 사용한다. 활동 페이지는 에이전트 스냅샷과 별개다. 실제 기록, 인증, 환경 값은 사용하지 않는다. 기존 설치 의존성만 사용하고 새 설치나 네트워크 요청을 하지 않는다.

후속 생성 단위 테스트와 브라우저 테스트에는 TC13(공급자), TC14(세션), TC18(선택 삭제)을 각각 반드시 구현한다. 최종 화면뿐 아니라 새 스냅샷 이전의 과도 상태와 이전 상세/활동 부재를 단언한다. 필터로 숨긴 선택과 실제 삭제를 별도 상태로 검증한다. 동일 ID를 새 범위에 재사용하여 ID만 비교하는 결함을 탐지한다.

## 실행·판정·결함 반환

테스트팀은 합성 자료와 기대값 검토 → 단위 → 브라우저 → 관련 회귀/빌드 → 변경 경계 검토 순으로 진행한다. 각 케이스는 PASS, FAIL, BLOCKED, NOT RUN 중 하나와 요약 근거를 기록한다. 이 단계 모든 케이스는 NOT RUN이고 C01의 의미 확정은 BLOCKED다. 개념 예시나 설계 설명은 실행 증거가 아니다.

결함 보고에는 케이스/요구사항 ID, 합성 사전조건, 재현 절차, 기대/실제 결과의 요약, 영향, 심각도, 개발 반환 및 재검증 상태를 기록한다. 민감 노출·프로젝트 혼입·이전 범위 상세 노출은 출시 차단 결함이다. 검색/상태/집계/선택 계약 위반 및 필수 동작 접근 불가는 주요 결함이다. 테스트팀은 제품 코드를 수정하지 않고 개발팀이 수정한다. 테스트 삭제·기대값 약화로 통과시키지 않는다.

수정 후 동일 재현 케이스와 영향을 받는 검증 층을 재실행한다. 범위 전환 수정이면 TC13–TC19와 TC23, 필터 수정이면 TC01–TC12 및 TC27을 확인한다. 새 변경이나 실패 없이 반복 실행하지 않는다.

출시 게이트는 계약 충돌 해결, F01–F09/P01–P06 충족, 필수 단위/브라우저 케이스 실행 통과, 관련 회귀·빌드 결과 확보, 출시 차단 및 주요 결함 해결, 제품/QA 검토와 출시 승인 기록이다. 미실행을 통과로 취급하지 않는다. 승인 후에만 운영팀이 별도 허용된 운영 단계에서 로컬 배포한다. 이 격리 단계에서는 배포·네트워크·설치·Paperclip·커밋·push를 하지 않는다.
